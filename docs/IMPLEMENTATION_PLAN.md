# Поэтапный план реализации SSH Session

## 1. Цель и границы

Проект предоставляет TypeScript API и терминальный CLI поверх системного OpenSSH. На первом этапе он не реализует протокол SSH самостоятельно и не содержит GUI.

Используемые программы:

- `ssh` — интерактивная сессия и выполнение удалённых команд;
- `scp` — загрузка и скачивание файлов;
- `sftp` — интерактивная работа с файлами и пакетные файловые операции.

Основные требования:

- ноль сторонних runtime-зависимостей;
- запуск процессов только через `spawn()` с `shell: false` и массивом аргументов;
- использование пользовательских `ssh_config`, `known_hosts` и `ssh-agent`;
- пароль или passphrase никогда не передаются в аргументах процесса, environment, файлах конфигурации или логах;
- неизвестный либо изменившийся ключ сервера не принимается незаметно;
- ядро не зависит от CLI, чтобы позднее его можно было подключить к GUI.

В первую версию не входят собственная реализация SSH/SFTP, хранение паролей, синхронизация каталогов и гарантированное восстановление оборванной shell-сессии.

## 2. Входные сценарии подключения

Все сценарии преобразуются в единый внутренний `ConnectionRequest`. Общие необязательные параметры: `port`, `connectTimeout`, `overallTimeout`, `configFile`, политика проверки host key и режим выделения TTY.

### 2.1. Host из `~/.ssh/config`

Вход:

```text
host
```

Поведение:

1. Передать alias программе OpenSSH без самостоятельного разбора `~/.ssh/config`.
2. При необходимости получить эффективную конфигурацию через `ssh -G <host>`.
3. Не переопределять `User`, `Port`, `IdentityFile`, `ProxyJump`, `ProxyCommand` и другие параметры без явного входного значения.
4. Если передан `configFile`, использовать `-F <path>` во всех связанных командах.
5. Аутентификацию, заданную в config, выполняет OpenSSH; интерактивные запросы остаются доступны пользователю.

Риски:

- alias отсутствует или содержит ошибку;
- `Include`, `Match`, `CanonicalizeHostname`, `ProxyJump` и `ProxyCommand` меняют фактический маршрут;
- один alias указывает на другой hostname или нестандартный порт;
- config может ссылаться на отсутствующий ключ или недоступный jump host;
- пользовательская конфигурация считается доверенной локальной конфигурацией и может запускать настроенные пользователем внешние команды.

### 2.2. Host, user и готовый password

Вход:

```text
host, user, password, port?
```

Поведение:

1. Запустить `ssh` для `user@host`, при необходимости указав порт.
2. Ограничить предполагаемый способ аутентификации password/keyboard-interactive, не позволяя случайному ключу скрыть ошибку сценария.
3. Передать пароль через ASKPASS broker и одноразовый локальный IPC-канал.
4. Не принимать пароль как CLI-флаг или позиционный аргумент. CLI получает его скрытым prompt; библиотечный API — через in-memory secret provider.
5. После завершения аутентификации закрыть IPC, удалить ссылки на секрет и очистить изменяемый буфер, насколько это возможно в Node.js.

Ограничения:

- строки JavaScript нельзя гарантированно стереть из памяти, поэтому внутри используется изменяемый буфер и минимальное время жизни секрета;
- готовый пароль нельзя автоматически подставлять в неизвестные MFA/OTP prompts;
- повторная выдача пароля ограничивается, чтобы не вызвать блокировку учётной записи;
- password authentication может быть запрещена сервером;
- `BatchMode=yes` использовать нельзя, так как он отключает password prompts.

### 2.3. Host, user и key_name

Вход:

```text
host, user, key_name, port?
```

Поведение:

1. Если `key_name` — простое имя, разрешить его относительно `~/.ssh/`.
2. Явный абсолютный путь принимать как путь к identity file.
3. До запуска проверить существование и тип файла, но окончательную проверку формата и прав оставить OpenSSH.
4. Передать ключ через `-i <path>` и включить `IdentitiesOnly=yes`, чтобы результат не зависел от случайных ключей агента.
5. Если ключ зашифрован, passphrase запрашивается интерактивно либо передаётся через тот же ASKPASS broker, но как отдельный тип секрета.

Риски:

- файл отсутствует, имеет неверный формат или слишком открытые права;
- выбран публичный ключ вместо приватного;
- ключ зашифрован, но passphrase не предоставлен;
- сервер отклоняет алгоритм или соответствующего public key нет в `authorized_keys`;
- сертификат ключа истёк либо не доверен сервером.

## 3. Единая модель запуска OpenSSH

Создать один внутренний process runner для `ssh`, `scp`, `sftp`, `ssh-keygen` и диагностического `ssh -G`.

Runner обязан:

- принимать executable и массив аргументов, но никогда командную строку оболочки;
- запрещать NUL, переводы строк и destination, начинающийся с `-`;
- не предоставлять произвольные OpenSSH options недоверенному вызывающему коду;
- поддерживать режимы `inherit`, `capture` и позднее `pty` через заменяемый адаптер;
- возвращать exit code, signal, длительность и безопасные диагностические данные;
- поддерживать `AbortSignal`, connect timeout, общий timeout и prompt timeout;
- корректно завершать дочерний процесс и не оставлять ASKPASS/IPC после отмены;
- маскировать секреты и не включать их в debug output;
- различать ошибку запуска процесса и ненулевой exit code OpenSSH.

Для интерактивной shell-сессии используется `stdio: inherit`. Для команд и пакетной передачи используется управляемый stdin/stdout/stderr с ограничением размера захватываемой диагностики.

Перед первой операцией команда `doctor` проверяет наличие и версии `ssh`, `scp`, `sftp` и `ssh-keygen`.

## 4. ASKPASS broker

ASKPASS нужен для готового password и, при необходимости, passphrase ключа.

### 4.1. Схема работы

1. Родительский Node.js-процесс создаёт локальный IPC endpoint и случайный одноразовый token.
2. Пароль хранится только в памяти родителя.
3. Для дочернего OpenSSH задаются путь к нашему helper в `SSH_ASKPASS` и `SSH_ASKPASS_REQUIRE=force`.
4. Helper получает текст prompt от OpenSSH, подключается к IPC и передаёт prompt родителю.
5. Родитель классифицирует prompt и возвращает password только разрешённому запросу.
6. После допустимого числа обращений либо завершения процесса endpoint закрывается.

На Windows используется named pipe, на Unix — Unix domain socket. В environment допускается только адрес IPC и одноразовый token, но не секрет.

### 4.2. Типы prompt

- password — можно ответить переданным password;
- key passphrase — можно ответить только явно предоставленной passphrase;
- host authenticity/fingerprint — требует отдельного решения по политике доверия;
- MFA/OTP/unknown — автоматически секретом не заполняется, запрос передаётся пользователю либо операция завершается понятной ошибкой;
- повторный password prompt — трактуется как возможный неверный пароль и ограничивается по числу попыток.

ASKPASS helper не должен сам принимать решения о доверии и не должен иметь постоянного доступа к секрету.

## 5. Fingerprint и `known_hosts`

OpenSSH остаётся единственным владельцем проверки и формата `known_hosts`. Проект не пишет этот файл самостоятельно.

### 5.1. Политики

Поддержать три явные политики:

- `ask` — безопасное значение по умолчанию; показать fingerprint и запросить подтверждение;
- `accept-new` — только по явному выбору; автоматически добавить новый ключ, но отклонить изменившийся;
- `strict` — принимать только уже известные ключи, без пользовательского prompt.

`StrictHostKeyChecking=no` проект не использует.

При ASKPASS prompt с fingerprint родитель показывает исходный текст OpenSSH. Готовый password никогда не используется как ответ на этот prompt.

### 5.2. Новый host key

В режиме `ask` пользователь должен подтвердить fingerprint. Перед подтверждением интерфейс предупреждает, что fingerprint следует сверить по доверенному каналу. `ssh-keyscan` можно использовать только для получения ключа, но не как доказательство его подлинности.

В неинтерактивной операции неизвестный ключ приводит к ошибке, если заранее не выбран `accept-new`.

### 5.3. Изменившийся или конфликтующий ключ

При `REMOTE HOST IDENTIFICATION HAS CHANGED` операция всегда останавливается. Автоматически удалять старую запись запрещено.

Диагностика должна:

1. Получить эффективные hostname и port через `ssh -G` там, где это возможно.
2. Учесть форму `[host]:port` для нестандартного порта.
3. Показать совпадающие записи через безопасный вызов `ssh-keygen -F`.
4. Объяснить возможные причины: переустановка сервера, смена ключей, повторное использование IP, DNS/proxy mismatch либо атака.
5. Предложить пользователю отдельно сверить новый fingerprint.
6. Показать команду `ssh-keygen -R`, но выполнять её только по отдельной прямой команде пользователя.

Нужно учитывать hashed `known_hosts`, разные alias одного сервера, IPv4/IPv6, нестандартный порт, jump host и несколько допустимых host key algorithms.

## 6. Установка интерактивной SSH-сессии

Команда:

```text
ssh-session connect <target>
```

Этапы:

1. Нормализовать и проверить `ConnectionRequest`.
2. Проверить наличие `ssh`.
3. Подготовить аргументы, trust policy и при необходимости ASKPASS broker.
4. Запустить `ssh` с наследованием терминала.
5. Перевести состояние `starting` в `running` только после наблюдаемого успешного запуска процесса; не обещать точное определение момента завершения SSH-аутентификации без протокольной поддержки.
6. Передать пользователю управление терминалом.
7. После выхода вернуть exit code, signal и состояние `completed`, `cancelled` либо `failed`.
8. В `finally` закрыть IPC и остальные временные ресурсы.

Следует учитывать изменение размера терминала, Ctrl+C/Ctrl+Break, закрытие родительского терминала, обрыв сети и зависание на prompt. После обрыва TCP shell-сессия не восстанавливается; для продолжения процессов на сервере пользователь применяет `tmux`/`screen`.

## 7. Выполнение удалённых команд

Команда:

```text
ssh-session exec <target> -- <remote-command>
```

Правила:

- по умолчанию не выделять PTY (`-T`), чтобы stdout/stderr подходили для автоматизации;
- выделять PTY только по явной опции для `sudo`, TUI или программ, требующих терминал;
- явно моделировать удалённую команду как строку для remote shell, а не обещать передачу независимого argv;
- не пропускать remote command через локальную shell;
- поддержать stdin в режимах `inherit`, `pipe` и `null`;
- сохранять stdout и stderr раздельно в неинтерактивном режиме;
- ограничивать объём capture либо предоставлять потоки;
- возвращать exit code удалённой команды.

OpenSSH возвращает `255` при собственной ошибке, но удалённая команда также способна завершиться с `255`; это не всегда можно различить достоверно. Классификация по stderr является best effort, а исходный exit code и безопасная диагностика сохраняются всегда.

Особые случаи:

- команда отсутствует или несовместима с удалённой shell;
- quoting отличается между POSIX shell, PowerShell и `cmd.exe`;
- `sudo` запрашивает TTY или пароль;
- соединение оборвалось после запуска команды, поэтому её фактическое состояние неизвестно;
- timeout локального клиента не гарантирует остановку уже запущенного удалённого процесса;
- stdout может быть бинарным и не должен безусловно декодироваться как UTF-8.

## 8. Передача файлов через `scp`

Команды:

```text
ssh-session upload <target> <local-path> <remote-path>
ssh-session download <target> <remote-path> <local-path>
```

`scp` использует тот же `ConnectionRequest`, trust policy и ASKPASS broker, что и `ssh`.

Требования:

- корректно учитывать различие флагов порта: `ssh -p`, но `scp -P`;
- сначала поддержать один файл, затем явную опцию recursive для каталогов;
- не включать overwrite, preserve times, compression и bandwidth limit без явной опции;
- проверять существование локального source перед upload;
- не считать destination безопасным только потому, что он передан отдельным argv: синтаксис `host:path`, IPv6, двоеточия и ведущий `-` требуют отдельной валидации;
- при обрыве отмечать результат как потенциально частичный;
- не обещать атомарность замены удалённого файла;
- в терминальном режиме отдавать прогресс самому `scp`, не парсить нестабильный человекочитаемый progress output.

Каждый запуск `scp` создаёт отдельное SSH-соединение и отдельный ASKPASS scope. Переиспользование соединения через OpenSSH multiplexing рассматривается после базовой версии.

## 9. Передача файлов через `sftp`

Предусмотреть два режима.

### 9.1. Интерактивный режим

```text
ssh-session files <target>
```

Запустить `sftp` с наследованием терминала. Пользователь получает стандартные команды `ls`, `get`, `put`, `mkdir`, `rename`, `rm` и другие возможности установленной версии OpenSSH.

### 9.2. Batch-режим

Использовать `sftp -b -` и передавать заранее построенный набор команд через stdin. Password/passphrase при этом обслуживаются отдельным ASKPASS IPC, а не stdin.

Требования:

- реализовать безопасное quoting путей с учётом синтаксиса именно SFTP batch-команд;
- запретить непроверенную вставку переводов строк и дополнительных команд;
- считать batch неуспешным при первой обязательной ошибке;
- явно отмечать частично выполненный batch: предыдущие операции не откатываются;
- не парсить интерактивный вывод как стабильный машинный API без подтверждённых тестов для поддерживаемых версий;
- протестировать ASKPASS вместе с `-b -` отдельно на каждой поддерживаемой ОС.

## 10. Классификация ошибок

Создать стабильные категории приложения, сохраняя исходное сообщение OpenSSH:

- `executable_not_found`;
- `invalid_input`;
- `config_error`;
- `dns_failed`;
- `connection_refused`;
- `connection_timeout`;
- `proxy_failed`;
- `host_key_unknown`;
- `host_key_changed`;
- `authentication_failed`;
- `key_unreadable`;
- `key_passphrase_required`;
- `mfa_required`;
- `permission_denied`;
- `connection_lost`;
- `remote_command_failed`;
- `transfer_failed`;
- `cancelled`;
- `unknown_openssh_error`.

Текст stderr зависит от версии, ОС и locale, поэтому распознавание является best effort. Логика приложения не должна зависеть только от английской строки ошибки.

## 11. Этапы реализации

### Этап 1. Каркас и контракты

- создать TypeScript-проект;
- определить типы `ConnectionRequest`, `AuthStrategy`, `HostKeyPolicy`, `ProcessResult` и `SshError`;
- отделить application API от CLI;
- определить правила redaction и валидации входа.

Готово, когда типами представлены все три сценария и ни один секрет не сериализуется.

### Этап 2. Process runner и `doctor`

- реализовать безопасный `spawn` без shell;
- добавить отмену, timeout, capture/inherit и очистку ресурсов;
- проверить `ssh`, `scp`, `sftp`, `ssh-keygen` и их версии;
- покрыть runner unit-тестами через внедряемый process adapter.

Готово, когда отсутствующая программа и ошибка запуска отличаются от exit code дочернего процесса.

### Этап 3. Разрешение target и аргументов

- реализовать три builder-а входных сценариев;
- добавить `ssh -G` для диагностики config host;
- унифицировать различающиеся аргументы `ssh`, `scp` и `sftp`;
- проверить option injection, пути, IPv6 и нестандартные порты.

Готово, когда builders детерминированно создают проверяемые массивы argv без запуска shell.

### Этап 4. Host key trust

- реализовать политики `ask`, `accept-new`, `strict`;
- добавить диагностику unknown/changed key;
- реализовать только чтение через `ssh-keygen -F`;
- подготовить отдельную, но не автоматическую операцию удаления после подтверждения пользователя.

Готово, когда изменившийся ключ никогда не принимается автоматически.

### Этап 5. ASKPASS broker

- реализовать одноразовый IPC и helper;
- классифицировать password, passphrase, fingerprint и unknown prompts;
- ограничить повторы и время ожидания;
- проверить отсутствие секрета в argv, env, временных файлах и логах;
- обеспечить cleanup при success, error, timeout и cancellation.

Готово, когда готовый password работает без появления в списке процессов и диагностике.

### Этап 6. Интерактивный `ssh`

- реализовать `connect` для трёх сценариев;
- подключить host key policy и ASKPASS;
- обработать exit, signal и пользовательскую отмену;
- сохранить нативное терминальное поведение OpenSSH.

Готово, когда доступны config host, password и key_name, включая первый fingerprint prompt.

### Этап 7. `exec`

- реализовать выполнение команды без PTY по умолчанию;
- добавить явный PTY mode;
- реализовать streaming/capture и передачу stdin;
- возвращать exit code без подмены;
- документировать remote-shell quoting и неопределённость после сетевого обрыва.

Готово, когда текстовый и бинарный вывод не теряется, а отмена не оставляет локальный `ssh`-процесс.

### Этап 8. `scp`

- реализовать upload/download одного файла;
- затем добавить recursive и прочие явные опции;
- подключить общую аутентификацию и host key policy;
- сообщать о возможности частичного файла после сбоя.

Готово, когда все три способа подключения одинаково работают для upload и download.

### Этап 9. `sftp`

- реализовать интерактивный `files`;
- добавить безопасный batch builder;
- проверить password ASKPASS при `sftp -b -`;
- описать неатомарность набора файловых операций.

Готово, когда batch-команды нельзя расширить через перевод строки в пользовательском пути.

### Этап 10. Надёжность и совместимость

- протестировать неизвестный, известный и изменившийся host key;
- протестировать неверный password, encrypted key, MFA prompt и исчерпание попыток;
- протестировать timeout, DNS failure, proxy failure, disconnect и cancellation;
- проверить Windows и минимум одну POSIX-систему;
- проверить разные locale OpenSSH;
- провести тесты отсутствия секретов в логах и process arguments.

Готово, когда ошибки имеют стабильную категорию либо честно попадают в `unknown_openssh_error` с безопасной исходной диагностикой.

### Этап 11. Подготовка к GUI

- сохранить интерфейс запуска процесса заменяемым;
- не связывать application API с `process.stdin/stdout`;
- представить prompts и события сессии структурированными событиями;
- предусмотреть будущий PTY adapter (`node-pty`) без включения его в текущую версию;
- оценить OpenSSH multiplexing для повторного использования аутентифицированного соединения.

Готово, когда CLI является только одним из consumers ядра.

## 12. Проверки перед выпуском

- unit-тесты builders, redaction, prompt classification и error classification;
- integration-тесты только на локальном изолированном SSH server с временными ключами;
- ручная проверка полноэкранного приложения в интерактивной сессии;
- ручная проверка password, key, encrypted key и config alias;
- upload/download через `scp` и интерактивный/batch `sftp`;
- проверка cleanup после Ctrl+C, timeout и аварийного завершения;
- проверка, что проект никогда не добавляет `StrictHostKeyChecking=no` и не удаляет `known_hosts` без отдельной команды.

Запуск integration-тестов и любые подключения к реальным внешним серверам выполняются только по отдельному прямому запросу пользователя.
